# Обновления и установщик: текущий срез

Закреплённый стандарт: game-spec-templates `0c2d4562683252d54736f294dc1af463050eac17`, updates0.2.1/installer0.1.0. Это описание исходников текущей ветки, не опубликованного релиза.

## Обновляющий клиент

За процесс выполняется одна discovery. Ошибка не включает ручную кнопку или автоматический повтор. Старт гонки не зависит от проверки версий. Перед её подготовкой updater отменяет и дожидается завершения всех своих запросов (discovery, дата публикации, история, выбранная загрузка). До конца гонки сеть запрещена; меню возобновляет загрузку того же пакета, не выбирая новую версию. Загрузка может начать пакет заново: докачка байтов не заявляется.

История запрашивает до десяти страниц GitHub Releases, выбирает десять последних версий своего канала по SemVer и отдельно включает установленный tag, если он вне выборки. Источник текста — body соответствующего Release. Языковые маркеры: `## Русский` и `## English`; отсутствующий перевод показывается как недоступный. Запрос истории не изменяет выбранный update descriptor. Переключатель РУ/EN расположен в отдельной нижней строке панели; меняет только язык истории и сбрасывает прокрутку текста. Кнопки доступны мышью и через навигацию меню; выбор пакета не меняется.

Новый клиент отвергает unsigned даже при старом define `STAR_RACING_UNSIGNED_PRODUCTION`. Обычный release.py также отказывается публиковать unsigned. Исторические низкоуровневые инструменты и тестовые baseline сохранены отдельно; это не ослабляет новый клиент.

Тест bridge получает точные исходники опубликованного клиента0.3.5 (`197de14d3041c043053c8f9956a7452f567babd9`) из GitHub, компилирует их со старым opt-in и проверяет signed catalog schema1 на Windows/macOS. Используется временный тестовый ключ, без изменения production trust root. Это проверка исходного контракта; установка bridge на устройства ещё не проверена.

## Внешнее восстановление

`distribution/recovery/Program.cs` — отдельный .NET8 процесс. При будущей разрешённой упаковке включаются self-contained helpers win-x64/osx-arm64/osx-x64. На клиенте helper копируется вместе с native Velopack helper в writable persistentDataPath, за пределы заменяемого приложения. Предыдущий и новый пакеты проверяются по signed descriptor, размеру и SHA256 и сохраняются в отдельном recovery/packages, который не чистит Velopack.

Журнал: `persistentDataPath/desktop-recovery-TRACK/transaction.json`. Состояния: prepared → applying → pending-health → healthy; сбои → recovery-required. Запись атомарна через flush + replace; внешний процесс удерживает file lock. PID дополняется временем старта; инициатор передаёт token подготовленной транзакции. Смена подготовленного пакета не разрешает старому инициатору применить новую цель.

Unity ничего не заменяет сама. Внешний процесс ждёт выхода игры и её других копий, запускает native apply через закреплённый SDK, затем новую игру с одноразовым health token. Health подтверждается после загрузки пользовательских данных, проверки релизного Default и первого отрисованного главного меню; совпадение версии и receipt не являются ack. Предыдущий verified package сохраняется до такого подтверждения. Если новая игра падает/не подтверждает готовность, процесс записывает recovery-required и один раз восстанавливает предыдущий подписанный пакет после выхода всех экземпляров. После таймаута живую игру не закрывает и не заменяет. Повторный запуск способен возобновить незавершённый журнал; journal предотвращает повторную активацию сбойной цели. Если восстановление невозможно, остаётся явное состояние с необходимостью переустановки и сохранением пользовательских данных.

Активация и обычный выход используют dirty guard лаборатории. Пользовательские настройки, рекорды и профили не копируются поверх данными recovery.

## Описание релизов по Git

`distribution/changelog.py` получает точный диапазон Git от `sourceRevision` предыдущего канала до публикуемой ревизии (в первом релизе — всю историю). Review JSON группирует все коммиты, включая merges, в понятные игроку исходы с `category: added/improved/fixed`, `ru`, `en`, `commits`. Для внутренних изменений допускается `internal: [{commits, reason}]`. Каждый реальный SHA диапазона должен быть покрыт ровно один раз; чужие/пропущенные SHA и пустой перевод запрещены. Генератор не копирует subjects и не выводит SHA/ID задач в Release body. Категории без изменений опускаются. Равнозначность переводов проверяет автор review.

Review содержит `schema:1`, `base:<SHA или null>`, `head:<SHA>`, `changes:[...]`, `internal:[...]`. Перед выпуском файл должен входить в подготовленную и проверенную исходную ревизию либо передаваться из отдельного согласованного release evidence; точные base/head проверяются независимо от размещения файла. В release.py используется `--changelog-review /absolute/review.json`; старый `--notes` отвергается. Read-only генерация:

```sh
python3 distribution/changelog.py --repo /absolute/source --base PREVIOUS_SOURCE --head SOURCE --review /absolute/review.json --output /absolute/notes.md
```

При будущем подписанном выпуске release.py также читает обратно пакет предыдущего канала, сверяет размер/hash и выпускает подписанный recovery-baseline-PLATFORM.json в **новом** Release. Старые immutable Releases не редактируются. Если предыдущий канал был unsigned, это явное подписание проверенных ранее опубликованных байтов тем же pinned ключом; не замена существующего пакета.

## Windows: восстановление и установка поверх

Мастер определяет HKLM InstallLocation и проверяет маркер установки, sq.version, app ID, канал и SemVer. Для той же версии предлагает «Восстановить», для новой — установку поверх в исходную папку. Downgrade, смешение stable/test и посторонняя непустая папка отвергаются. Если sq.version утрачен, версия не выдумывается: мастер объясняет причину отказа. Настройки/рекорды/Lab вне install root не меняются; посторонние файлы внутри root сохраняются.

Payload извлекается в соседнюю папку `ROOT.sr-stage-TOKEN`. Внешний helper сохраняет журнал `ROOT.sr-install.json` до первого перемещения и переносит только именованный список файлов/папок. Старые файлы остаются в `ROOT.sr-backup-TOKEN` до успешной регистрации и commit. Ошибка перемещения восстанавливает прежние байты; следующий запуск восстанавливает незавершённый applying-журнал. Завершённый журнал допускает повторную очистку. Финальный мастер принимает только receipt текущего одноразового token; старый marker/receipt не подтверждает новую попытку.

Игра удерживает handle общего Windows mutex с самого bootstrap до выхода. Helper получает эксклюзивный допуск на время замены/удаления; запуск во время замены прекращается до загрузки Unity. Дополнительная проверка процессов защищает установленные старые клиенты без этого контракта. Живые процессы не завершаются автоматически. Symlink/junction в заменяемом дереве отвергаются. Удаление использует тот же helper, сохраняет userdata и посторонние файлы, а при незавершённом журнале просит сначала закончить восстановление. Пустой sibling `.sr-install.lock` намеренно остаётся как стабильная точка блокировки.

## Тихий запуск и проверка

Установленная Windows-игра: `"C:\Program Files\Star Racing\Star Racing.exe" -noaudio -muted`.

macOS: `"/absolute/Star Racing.app/Contents/MacOS/Star Racing" -noaudio -muted` (укажите фактическую папку установки). Launcher передаёт аргументы без потери. Recovery сохраняет исходные `-noaudio -muted` при перезапуске; системная громкость и сохранённые громкости не меняются.

Affected-команды и результаты — в `planning/evidence/align-game-template-standards/desktop/QA-PLAN.txt`. Полный прогон, Player/shipping/installer builds и публикация не запускались. Реальный установленный A→B→A, Windows repair/reinstall, macOS/Windows device/install/human acceptance остаются открытыми. Сценарии установленного repair требуют отдельной проверки на Windows; source/process fixtures их не заменяют.

## Независимый лаунчер (add-desktop-launcher)

Production-релиз 0.3.16 добавляет предварительный запуск и native-вопрос обновления по образцу Star Tournament. Авторизация загрузки привязана к конкретной версии и текущему запуску. Отказ/офлайн/отмена запускают существующую игру; первый запуск новой версии должен подтвердить готовность до последующих предварительных активаций. Windows сохраняет старый target ярлыков `Star Racing.exe`; macOS меняет CFBundleExecutable на универсальный entry при сохранении Unity identity и Player. Лаунчер передаёт argv без shell, включая `-noaudio -muted`, и ждёт реальный Player. Recovery проверяет новый launcher entry, затем принимает одноразовое сообщение с реальным Unity PID и ожидает health именно этого Player. Перед заменой ждёт также исходный supervisor launcher. Старый signed schema-2 Star Racing не заменяется протоколом Star Tournament. Автоматические fixtures и fake-child probe не означают installed Windows/macOS A→B→A приёмку.
