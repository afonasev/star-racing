# Правила публикации Star Racing

Обычный выпуск выполняется только через `distribution/release.py` в репозитории https://github.com/afonasev/star-racing. Пакеты и проверка версий новых клиентов работают через GitHub Releases. Изменять VPS при каждом выпуске не нужно.

## Подготовка и каналы

- Готовить изменения в отдельной ветке/worktree, сохранять чужую работу, выполнить подходящие проверки. Публиковать из чистой закоммиченной ревизии, уже доступной на GitHub.
- Release Mac: Unity 6000.3.23f1 с Windows/macOS-модулями, Python 3.11+, OpenSSL, GitHub CLI с доступом к репозиторию/Actions, MinGW g++/windres. Workflow `windows-wizard.yml` должен быть в default branch. Закреплённые SDK/Velopack и их хеши находятся в `distribution/toolchain.json`.
- Приватный RSA-ключ хранить вне Git, приложения, CI и VPS. Передавать только путь через `STAR_RACING_SIGNING_KEY` или `--key`. Он должен соответствовать `distribution/update-public.pem`.
- `test`: prerelease SemVer и указатель `channel-test`; `production`: stable SemVer и `channel-production`. Версия и положительный Int32 sequence возрастают внутри своего канала. Перед выпуском прочитать текущий указатель и выбрать новые значения.
- Production требует отдельной явной авторизации и физической приёмки Windows/macOS. Скрипт не подтверждает их за человека. Тестовый Player нельзя превратить в production простым переключением флага релиза.
- Не перезаписывать существующие версии, включая draft, и их файлы. Подпись метаданных не заменяет Authenticode/Developer ID/notarization; тестовые установщики пока без этих сертификатов.

## Команды

Из корня чистого публичного проекта; значения версии/sequence ниже — пример, перед следующим выпуском проверить канал:

```sh
STAR_RACING_SIGNING_KEY=/absolute/private/update-private.pem \
python3 distribution/release.py --track test --version 0.2.2-test.3 --sequence 11 \
  --notes 'Описание изменений для игрока'
```

Прочитать машиночитаемые правила без ключа, сборки или обращения к GitHub:

```sh
python3 distribution/release.py --show-policy
```

## Порядок и ошибки

Команда проверяет исходники/канал, создаёт reservation `_publishing-TRACK`, собирает обе платформы и упаковывает их. Затем создаёт draft; GitHub Actions собирает Windows wizard из точного SHA исходников и portable SHA256. Подписи метаданных платформ, версий, размеров, SHA256 пакетов и установщиков создаются локально. После загрузки всех файлов проверяются комплектность, размеры, API digest и SHA256 реального обратного скачивания. Сначала публикуется полная версия, затем последним переключается указатель выбранного канала. Reservation снимается в `finally`.

Ошибка до успешного readback оставляет draft и прежний указатель. Сохранить логи/SHA/workflow/evidence, исправить причину и выбрать новую версию; не обходить проверки и не использовать `--clobber`. Если версия опубликована, а указатель не переключён, сохранить и разобрать это состояние, не пересобирать и не редактировать опубликованные файлы.

После аварии reservation может остаться. Сначала подтвердить остановку владельца, проверить SHA/релиз/указатель и сохранить evidence. Не удалять чужой или активный lock. Unity запускать через `tools/unity.sh`; чужие процессы/кэши не трогать.

## Проверки и сохранение

Команды проверок и live-download через настоящий код updater описаны в [distribution/README.md](../distribution/README.md). Проверить обе платформы, реальные подписи/размеры/SHA256 пакетов, браузерные ссылки лендинга, CORS/redirects и хеши установщиков.

Физическая приёмка отдельная: Windows установка/UAC/ярлык/две галочки/обычный запуск/удаление; macOS PKG/Apple Silicon/Intel; обе платформы — фоновые загрузки, отмена/обрыв, отказ прав, Restart и следующий обычный запуск, сохранение профилей. Автотесты и компиляция не подтверждают эти проверки.

Перед очисткой сохранить `.local/releases/VERSION/evidence`, обе `identity.json`, подписанные дескрипторы, `manifest.json`, readback/хеши и точные опубликованные артефакты для приёмки. Затем удалить только свои промежуточные сборки, кэши, дубликаты скачиваний и завершённые worktree/ветки; перепроверить Git и процессы. Открытую приёмку не архивировать.

## Установка, лендинг и миграция

Имена: `Star-Racing-VERSION-Windows-Setup.exe`, `Star-Racing-VERSION-macOS-Setup.pkg`. Сохранять существующую иконку, Program Files с UAC и две отмеченные галочки последнего экрана. Обычный запуск игры не требует администратора; профили находятся вне заменяемого payload. NSIS-деинсталлятор сохраняет исходный `$INSTDIR`, не подменяет его временным `$EXEDIR`.

Игра проверяет версию при запуске и вручную. Скачивание — только по «Обновить», в фоне; применение после выхода через «Перезапустить» либо при следующем обычном запуске. Ошибка/обрыв/отказ прав сохраняют рабочую игру.

Лендинг читает подписанный GitHub-указатель и оставляет версионные имена ссылок. Production не подменяется тестовым каналом автоматически. `distribution/migrate_legacy.py` — однократный мост после публикации и независимой проверки пакетов. Старые signed feeds и все allowlisted relay paths сохранять до подтверждения миграции. На VPS остаются небольшие метаданные/relay, дистрибутивы — в GitHub. `publish.py` и `github_publish.py` — исторические инструменты, не обычный новый выпуск.
